# 리허설에 필요한 Phase 2 일부 구현

## 범위

Phase 1의 실행 흐름 및 Phase 2의 FR-206, FR-512/513, FR-806 일부를 반영했다.
만족도와 종료 시 /feedback 라우팅, 전사·요약, 사전 과제, 계정·역할 관리, 출석 수동 보정은 이번 범위에서 제외했다.

- `/admin/data`: 종료된 회차의 출석·제출·미제출 상태와 시작·종료·실제 소요 시간. 명단이 없으므로 접속·작성자 기준으로만 집계한다.
- `/mine`: 로그인한 사람의 종료된 회차 제출물만 읽기 전용으로 표시한다. 타인 ID를 받지 않는다.
- `/admin/session/[id]`: 주제·질문 추가·수정·삭제·정렬. 시작 전이며 작성 기록이 없는 회차만 저장한다. API에서도 같은 조건을 확인한다.

## 함께 수정한 것

- 시드 재실행으로 운영진이 편집한 주제·질문이 덮어써지지 않게 했다.
- 폼 편집과 세션 제어는 동일한 DB 잠금을 사용한다. 참가자 폼 조회·저장도 이 경계와 동기화한다.
- 폼 저장은 기존 내용의 버전을 검증한다. 다른 창에서 변경된 폼을 조용히 덮어쓰지 않는다.
- 질문 순서 변경 시 고유 ID를 유지하고 임시 순서를 거쳐 DB 고유 제약 충돌을 피한다.
- 참가자의 운영진 페이지 접근은 실제 HTTP 403을 반환한다. 페이지의 DB 조회 전에도 운영진을 확인한다.
- 참가자 답변칸의 label과 textarea를 연결했다.

## 시나리오에 추가할 검증

1. 시작 전 회차에서 주제와 질문을 준비하고, 질문 추가·순서 변경 후 저장·새로고침한다.
2. 기존 Phase 1의 로그인 → 업로드 → 시작 → 장표 → 폼 → 제출 → 공유 → 휴식 → 3부 → 종료를 수행한다.
3. 종료 후 참가자는 `/mine`에서 자신이 제출한 내용을 확인한다. 다른 계정의 답변이 섞이지 않아야 한다.
4. 운영진은 `/admin/data`에서 출석·제출 상태와 네 구간의 시작·종료·실제 시간을 확인한다.
5. 진행 중 또는 종료된 회차의 폼 편집이 잠기는지 확인한다. 작성 기록이 있는 리허설은 초기화 후에도 보호한다.

## 이번 검증

- 기존 리허설 결과로 출석 2명·제출 1명·접속/작성자 중 미제출 1명과 네 구간 시간 표시를 브라우저에서 확인했다.
- `/mine`에서 기존 리허설 제출물 여섯 답변이 읽기 전용으로 표시되는 것을 확인했다.
- 1주차 편집기에서 순서 변경과 질문 추가를 확인하고 원래 구성으로 복원했다. 기존 여섯 질문·순서·주제 그대로 실제 Supabase 저장 성공을 확인했다. 실제 회차는 시작하지 않았다.
- 종료된 리허설 폼은 입력 비활성화, 저장 버튼 없음으로 확인했다.
- 회귀 테스트 32개 통과. 인증/DB 대체 테스트이므로 실제 다른 계정과 네트워크 차단 시험을 대체하지 않는다.
- Webpack 프로덕션 빌드와 타입 검사 수행.

남은 실환경 검증: 별도 참가자 계정에서 첫 제출, 타인 제출물 공유/차단, 네트워크 끊김 후 복구. 이 결과만으로 전체 리허설 합격을 선언하지 않는다.
