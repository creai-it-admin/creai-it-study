# Foundation 1주차 · 강의 노트

## 1. 지금의 AI를, 우리는 충분히 쓰고 있을까?

시작 질문: 최근 일주일 동안 AI에게 실제로 맡긴 가장 큰 일은 무엇이었나요? 검색, 문장 다듬기, 요약 중 어디에 머무르고 있는지 떠올려 보게 합니다. 답을 평가하지 말고 오늘의 출발점으로 삼습니다.
오늘은 특정 도구의 메뉴를 외우는 시간이 아닙니다. 현재의 AI를 내 업무에 연결할 수 있다는 감각과 최소한의 사용 기반을 만드는 시간입니다.
다음: 왜 지금 우리의 활용 범위를 다시 생각해야 할까요?

## 2. AI는 어려운 연구 문제에도 새로운 해법을 제시하고 있습니다.

처음부터 수학을 설명하려는 장이 아닙니다. 오랫동안 연구된 문제에서 AI가 해법을 생산하는 단계에 들어섰다는 점을 보여줍니다.
OpenAI는 2026년 9월 8일 내부 모델을 이용해 나비에–스토크스 문제의 해법과 Lean 형식화 결과를 발표했습니다. 핵심은 매끄러운 외력이 있는 조건에서 유한 시간 특이점이 생기는 구성입니다. 발표된 연구 결과와 독립적인 수학계 검증·상금 인정은 구분합니다.
이 결과에는 비공개 내부 모델과 대규모 에이전트 협업이 사용됐습니다. 우리가 쓰는 공개 모델에 질문 한 번 던져 얻은 성과로 소개하지 않습니다.
연결: 연구의 최전선뿐 아니라, 우리가 하는 업무에서는 어떤 수준일까요?

## 3. 전문가의 업무 결과물과 경쟁하는 역량도 확인되고 있습니다.

GDPval은 실제 지식 노동의 결과물을 비교하는 평가입니다. 문서·장표·스프레드시트 등, 44개 직업군의 명확하게 정의된 과제를 다룹니다.
여기서는 확인 가능한 공식 수치인 GPT-5.5의 84.9%를 사용합니다. 의미는 전문가가 만든 결과물과 비교해 이기거나 동률인 비율입니다. 인간보다 84.9% 더 똑똑하다는 뜻도, 모든 직업을 통째로 대체한다는 뜻도 아닙니다. 최신 모델 전체의 순위표로 제시하지 않습니다.
청중에게 강조할 점: 내가 중요하게 여기는 업무에서도 AI를 진지한 작업자로 시험할 이유가 충분해졌다는 것입니다.
연결: 이 역량을 한 번만 사용할 수 있는 것이 아니라면 어떤 차이가 생길까요?

## 4. 이 역량을 반복해서 요청하고, 여러 작업에 동시에 사용할 수 있습니다.

기계는 사람처럼 지루함이나 피로를 느끼지 않습니다. 덕분에 같은 요청을 여러 차례 검토·수정하게 하거나, 독립적인 작업을 별도 세션으로 진행할 수 있습니다. 다만 출력 품질이 언제나 동일하거나 무오류라는 뜻은 아닙니다.
이 장의 핵심은 높은 역량과 반복·병렬 수행을 함께 생각하는 것입니다. 하나를 더 시도할 때마다 반드시 사람의 노동 시간을 같은 비율로 추가할 필요는 없습니다.
병렬 세션과 서브에이전트는 구분합니다. 이 장은 작업을 여러 개 진행하는 가능성을 설명하고, 서브에이전트의 구조는 뒤에서 다룹니다. 비용·사용량·검토 가능 범위 안에서 운영합니다.

## 5. 일을 시작할 때, AI에게 무엇을 맡길지부터 생각해야 합니다.

앞선 증거에서 우리가 제안하는 행동 원칙으로 넘어가는 장입니다. AI를 반드시 모든 업무에 무비판적으로 적용하라는 뜻이 아닙니다. 일을 시작할 때 AI가 맡을 수 있는 부분을 먼저 떠올리는 습관을 제안합니다.
예를 들어 문서가 들어왔을 때 먼저 직접 다 읽는 것이 유일한 출발점인지, 자료를 읽고 구조를 정리하게 한 뒤 핵심을 확인할 수 있을지 생각합니다.
참가자에게 최근 스스로 처리한 일 하나를 떠올리게 합니다. 어떤 부분을 맡길 수 있었을까요? 구체적인 업무 설계는 2주차에서 이어갑니다.

## 6. 오늘은 이 지능을 실제 내 일에 사용할 기반을 만듭니다.

오늘의 도착점을 명확히 합니다. 어떤 모델과 도구를 쓸지, 도구에 어떤 기능이 있는지, 실제로 일을 요청하고 결과를 확인하는 기본 흐름을 배웁니다.
첫 주에 모든 기능을 설정하거나 능숙하게 사용할 필요는 없습니다. 무엇이 가능한지 알고, 도움을 받아 한 번 시작할 수 있으면 됩니다.
마지막에는 진행자의 코덱스 화면에서 랜딩페이지, 이미지 기반 덱, 스킬 제작을 함께 봅니다. 세 개의 과제를 숙제로 부과하는 것이 아니라 기능들이 실제 작업에 연결되는 것을 관찰하는 시간입니다.

## 7. 어지간하면 투자해서, 가장 좋은 모델부터 제대로 써보세요.

이 장은 CREAI+IT EDU의 활용 권고입니다. 무조건 가장 비싼 요금제를 사라는 주장이 아니라, 자신의 예산 안에서 높은 역량의 모델을 충분히 경험해 보라는 뜻입니다.
낮은 역량의 모델에서 여러 번 실패하고 수정하느라 자신의 시간을 많이 쓰면, 구독료만 비교했을 때와 실제 비용이 달라집니다. 먼저 좋은 모델로 무엇이 가능한지 감각을 얻고, 반복 업무를 이해한 뒤 적합한 모델을 고르는 순서가 좋습니다.
요금제는 특정 고정 가격으로 적지 않습니다. 강의 당일 화면에서 이용 가능한 상위 모델과 사용량을 확인합니다. 가장 비싼 모델이 모든 과제에서 항상 최고라는 주장은 하지 않습니다.

## 8. Codex와 Claude Code는 그 지능에게 실제 일을 맡기는 도구입니다.

두 제품 모두 네이티브 데스크톱 앱에서 이용한다는 전제로 소개합니다. 인터페이스나 접속 방식으로 차이를 나누지 않고, 작업 공간과 도구를 모델에 연결해 실제 일을 수행하는 공통 역할을 설명합니다.
두 도구 모두 앱에서 자료를 읽고, 작업을 요청하고, 생성된 파일과 실행 결과를 확인하는 흐름으로 설명합니다. 오늘의 실시간 워크스루는 강의자의 Codex 앱에서 함께 진행합니다.
코딩 에이전트라는 이름 때문에 코드만 다룬다고 생각하지 않도록, 문서·이미지·장표도 파일 형태의 업무 산출물이라는 점을 연결합니다.

## 9. 에이전트는 맥락과 도구를 연결해, 모델이 할 수 있는 일을 확장합니다.

가장 중요한 개념 설명입니다. 기본적인 자기회귀 언어 모델은 입력된 맥락을 바탕으로 다음 토큰을 생성하고, 이를 반복합니다. 토큰은 텍스트를 처리하는 작은 단위라고 설명하면 충분합니다.
에이전트는 이 생성 능력을 반복 실행 구조 안에 놓습니다. 모델이 도구 호출을 출력하면 프로그램이 실제 도구를 실행하고, 그 결과를 다음 맥락에 넣습니다. 모델은 새 정보를 바탕으로 다음 호출이나 답변을 생성합니다.
맥락에는 사용자의 요청뿐 아니라 읽어온 파일, 처리된 이미지 입력, 검색 결과, 오류 메시지, 실행 결과가 들어올 수 있습니다. 계산기·코드 실행기·파일 수정 도구는 정해진 기능을 실제로 수행합니다. 외부 도구에도 오류와 권한 제한은 존재합니다.
확장된다는 것은 모델의 추론 능력이 무한해진다는 의미가 아닙니다. 연결하는 자료와 실행 수단을 통해 수행 가능한 일의 범위가 넓어진다는 뜻입니다. 도식의 위쪽과 아래쪽을 번갈아 짚으며 설명합니다.

## 10. 이제, Codex와 Claude Code가 일하는 방식을 살펴봅시다.

개념에서 구체적인 기능으로 넘어가는 전환입니다. 앞 장에서 설명한 맥락과 도구가 실제 제품에서는 파일·실행·서브에이전트·지침과 스킬·외부 연결·권한으로 나타납니다.
이 여섯 가지를 각각 무엇인지, 어떤 일을 가능하게 하는지 중심으로 보겠다고 안내합니다. 메뉴 위치나 제품별 차이는 라이브 화면에서 짚고, 장표에서는 공통 원리를 유지합니다.

## 11. 로컬 작업 폴더가 에이전트의 작업 공간이 됩니다.

Codex나 Claude Code에서 로컬 프로젝트를 선택하는 장면과 연결합니다. 오늘 설명하는 로컬 사용 방식에서는 선택한 폴더가 작업의 기준점이 됩니다. 클라우드 실행에서는 별도의 작업 환경을 사용할 수 있습니다.
자료를 대화창에 매번 복사할 필요 없이, 에이전트가 허용된 경로의 파일을 찾아 읽게 할 수 있습니다. 결과 역시 대화 답변으로만 남는 것이 아니라 HTML, 이미지, 문서 등 파일로 저장됩니다.
오른쪽 세 동작을 실제로 짚습니다: 기존 자료를 읽기, 결과 파일 만들기, 수정하고 다시 보기. 폴더를 선택했다고 모든 파일이 자동으로 맥락에 전부 들어가는 것은 아니며, 필요한 내용을 탐색하고 읽습니다.
화면의 파일명은 구조를 설명하기 위한 예시입니다. 이 예시를 실제 완료 기록처럼 소개하지 않습니다.

## 12. 파일을 만드는 데서, 실행하고 확인하는 데까지 이어집니다.

파일을 작성했다고 일이 끝난 것은 아닙니다. 웹사이트라면 서버를 실행해 페이지를 확인하고, 문서라면 변환 또는 열람해 결과를 확인해야 합니다.
에이전트는 명령 실행 도구로 프로그램을 돌리고 오류 메시지를 읽을 수 있습니다. 필요한 경우 브라우저 도구로 화면을 확인할 수 있으나 별도 연결과 권한이 필요할 수 있습니다.
예시: 랜딩페이지를 만든 뒤 실행 과정에서 오류가 발생하면 그 메시지가 새 맥락이 되어 수정으로 이어집니다. 9장의 반복 구조가 실제로 보이는 순간입니다. 참가자가 명령어를 모두 외우는 것이 목표가 아니라, 무엇을 확인하게 해야 하는지 이해하는 것이 목표입니다.

## 13. 서브에이전트로 작업 일부를 나누어 맡길 수 있습니다.

메인 에이전트가 목표와 최종 결과를 담당하고, 독립적으로 맡길 수 있는 일부 작업을 별도 에이전트에 위임하는 구조입니다. 서브에이전트는 별도의 맥락에서 일하고 필요한 결과를 돌려줍니다.
예를 들어 같은 자료의 고객 관점, 기술 관점, 근거 확인을 각각 조사하게 할 수 있습니다. 동시에 진행할 수 있는 독립적인 작업에 특히 유용합니다. 앞 작업의 결과가 있어야 가능한 일은 순서가 필요합니다.
개수가 많을수록 항상 더 좋은 것은 아닙니다. 비용과 조율이 늘며 같은 파일을 동시에 고치면 충돌할 수 있습니다. 이번 주는 개념과 사용 가능성을 인지하고, 더 큰 업무의 분해와 검토 구조는 2주차에서 배웁니다.

## 14. 지침과 스킬로, 원하는 기준과 작업 방식을 재사용할 수 있습니다.

지침은 프로젝트에서 계속 지켜야 할 기준에 가깝고, 스킬은 특정 작업을 할 때 불러오는 절차와 참고 자료의 묶음에 가깝습니다. 제품마다 적용 범위와 탐색 방식은 다르지만, 반복 설명을 파일로 남긴다는 핵심은 같습니다.
Codex의 AGENTS.md, Claude Code의 CLAUDE.md를 예로 들고, 특정 작업의 스킬에는 SKILL.md와 필요시 참고 자료·스크립트가 들어갈 수 있다고 설명합니다.
좋은 스킬은 긴 지시문만 뜻하지 않습니다. 언제 사용할지, 어떤 자료를 확인할지, 무엇을 만들어야 하는지, 어떤 기준으로 확인할지를 담습니다.
스킬 파일 자체를 수정하거나 삭제하면 행동도 바뀔 수 있습니다. 오늘 마지막 워크스루에서 짧은 공지 작성 스킬을 직접 만들고 다시 호출해 봅니다.

## 15. 외부 서비스를 연결하면, 작업 공간을 더 넓힐 수 있습니다.

MCP는 모델 자체의 지식이 아니라 외부 데이터와 도구를 연결하는 표준 인터페이스입니다. 커넥터나 플러그인은 이런 연결을 제품에서 편하게 이용하도록 제공할 수 있습니다. 둘을 완전히 같은 단어로 취급하지 않습니다.
예를 들어 연결된 문서 서비스에서 관련 페이지를 찾아 읽고, 권한이 허용된 업무 도구에 변경을 반영하는 식입니다. 서비스 이름만 말하면 자동으로 접근 권한이 생기는 것은 아니며, 해당 연결의 설치·인증·권한이 필요합니다.
화면의 문서·메시지·업무 시스템은 연결 가능한 범주의 예시입니다. 모든 서비스의 모든 행동이 지원된다는 뜻은 아닙니다.
연결: 할 수 있는 일이 늘어나는 만큼, 무엇을 허용했는지 아는 것이 중요합니다.

## 16. 접근과 실행 권한을 이해해야, 어디까지 맡길지도 정할 수 있습니다.

에이전트는 설정된 권한과 실행 환경 안에서 행동합니다. 파일 읽기, 파일 수정이나 명령 실행, 외부 서비스 변경은 서로 다른 효과를 가집니다.
권한 화면에서 모든 요청을 기계적으로 승인하거나 거절하기보다, 지금 어떤 대상에 어떤 행동을 하려는지 읽게 합니다. 샌드박스 범위와 추가 승인 요구는 제품·환경별로 달라질 수 있습니다.
오늘 데모는 교육용 폴더를 사용하고, 외부 게시·메일 발송 등은 시연 범위에 포함하지 않습니다. 실제 사용자 자료와 외부 서비스에 대한 작업은 그 목적과 권한을 먼저 확인합니다.
이제 기능 소개가 끝났습니다. 다음 세 장에서는 코덱스 화면을 보면서 실제로 무엇이 일어나는지 함께 관찰합니다.

## 17. 랜딩페이지를 만들어봅시다.

실시간 워크스루 1: 진행자의 Codex 화면으로 전환합니다. 참가자들은 어떤 기능이 쓰이는지 함께 짚고, 결과를 본 뒤 수정 의견을 냅니다.
준비: 빈 교육용 폴더에 간단한 서비스 소개 문서를 둡니다. 브랜드·대상·주요 기능은 사실로 확인된 내용 또는 명확한 가상 데모 내용을 사용합니다.
시작 요청 예시: “이 폴더의 소개 자료를 읽고 랜딩페이지를 만들어 줘. 핵심 메시지와 구성을 먼저 제안한 다음 구현하고, 로컬에서 열어 확인해 줘.”
볼 것: 자료를 찾는 장면, HTML·스타일 등 파일이 생기는 장면, 실행 또는 브라우저 확인, 수정 요청이 파일에 반영되는 장면.
함께 할 질문: 지금 어떤 자료를 읽었나요? 결과는 어디에 저장됐나요? 화면에서 무엇을 고치고 싶나요?
완료 확인: 로컬 페이지가 열리고 핵심 메시지가 읽히며 한 번의 수정이 반영됩니다. 외부 배포는 이 워크스루의 완료 조건이 아닙니다.

## 18. 이미지 생성 기능으로 발표용 덱을 만들어봅시다.

실시간 워크스루 2: 이미지 생성 기능 또는 스킬이 연결된 Codex 환경을 사용합니다. 이미지 생성은 모델의 기본 텍스트 출력과 다른 도구 호출이라는 점을 9장의 구조와 연결합니다.
준비: 교육용으로 사용할 짧은 주제와 청중을 정합니다. 예를 들어 스터디 소개 3장으로 제한해 현장에서 과정이 보이게 합니다.
시작 요청 예시: “처음 오는 참가자에게 우리 스터디를 소개하는 3장 덱을 만들어 줘. 각 장의 메시지를 먼저 잡고, 이미지 생성으로 장표를 만든 다음 순서대로 볼 수 있게 묶어 줘.”
볼 것: 장별 메시지를 잡는 단계, 이미지 생성 도구가 호출되는 단계, 출력 이미지의 글자·일관성을 확인하는 단계, 발표용 파일에 조립하는 단계.
함께 할 질문: 가장 중요한 메시지가 한눈에 보이나요? 글자가 정확한가요? 세 장이 같은 덱처럼 보이나요?
완료 확인: 세 장을 순서대로 열 수 있고 내용·글자·순서를 검토합니다. 생성 시간이 길면 완료된 한 장의 검토를 먼저 진행하고 나머지 생성은 이어갑니다. 준비된 예시를 보여줄 경우 라이브 생성 결과와 명확히 구분합니다.

## 19. 반복해서 맡길 작업을, 재사용할 스킬로 만들어봅시다.

실시간 워크스루 3: 앞서 소개한 지침·스킬을 실제 파일로 만들어 다시 호출합니다. 기존 스킬을 덮어쓰지 않고 교육용 새 스킬을 만듭니다.
예시 작업은 매주 반복되는 스터디 안내문 작성입니다. 제목, 일정·장소, 다룰 내용, 준비사항을 일정한 형식으로 담는 작은 스킬이면 충분합니다.
시작 요청 예시: “확정된 일정과 세션 주제를 받아 참가 안내문을 쓰는 스킬을 만들어 줘. 없는 정보는 만들지 말고 확인하도록 해 줘. 이번 주 예시로 실행해서 결과까지 확인해 줘.”
볼 것: 언제 쓰는지와 작업 절차가 SKILL.md에 들어가는 장면, 다른 입력으로 같은 스킬을 다시 사용하는 장면, 빠진 정보가 있을 때 임의로 채우지 않는지 확인하는 장면. 제품의 지원 방식에 따라 스킬을 명시적으로 호출합니다.
완료 확인: 새 스킬 파일이 생기고, 두 번째 요청에서 그 스킬을 읽어 원하는 구조의 안내문을 만듭니다. 실제 참가자에게 발송하지 않습니다.

## 20. 이제 여러분의 일에서도, AI에게 맡길 부분부터 찾아봅시다.

처음 질문으로 돌아옵니다. 오늘 오기 전보다 맡길 수 있다고 생각하는 일의 범위가 달라졌는지 묻습니다.
참가자가 자신의 업무 하나를 떠올려 어떤 부분을 맡기고 어떤 결과를 직접 확인할지 한 문장으로 말할 수 있게 합니다. 별도의 숙제나 제출 형식을 여기서 확정하지 않습니다.
이번 주의 핵심은 높은 역량의 모델을 경험하고, 코딩 에이전트의 기능이 무엇을 가능하게 하는지 이해하며, 작업을 시작하고 결과를 확인하는 기본 흐름을 아는 것입니다.
다음 주에는 더 큰 업무의 목표와 맥락, 역할, 검토 지점을 설계하고 AI와 협업하는 구조를 다룹니다. 끝없는 기능 소개 대신 실제 업무 운영으로 연결합니다.
